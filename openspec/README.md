# Спецификации изменений (OpenSpec)

Как мы используем спеки в legacy-репозитории:

- **Спека только на то изменение, которое делаешь.** Не описываем систему целиком задним числом:
  как устроено сейчас — в `docs/`, а в `openspec/changes/<id>/` — только новое поведение.
- **Черновик пишет агент** по коду и тикету (скилл `.agents/skills/story-analysis/`):
  публичный контракт, сценарии WHEN/THEN, вне scope, «Готово». Вопросы без ответа — не выдумывает, а задаёт.
- **Владелец области читает спеку до кода.** Код пишем, только когда контракт и «Готово» подтверждены.
- **После мёржа изменение уходит в архив** (`openspec archive <id>`: папка переезжает в
  `openspec/changes/archive/`, дельта вливается в `openspec/specs/`). Правила, которые стали нормой
  для всех, переносим в `docs/`.

Структура изменения: `proposal.md` (зачем), `specs/<capability>/spec.md` (что — дельта-спека по
capability), `tasks.md` (шаги для агента).
Ключевые слова OpenSpec — `ADDED Requirements`, `Requirement`, `Scenario`, `WHEN`/`THEN`/`AND`, `SHALL` —
оставляем на английском: по ним спеку разбирают инструменты OpenSpec.

Пример: `changes/add-application-security/` со спекой `specs/application-security/spec.md`.
