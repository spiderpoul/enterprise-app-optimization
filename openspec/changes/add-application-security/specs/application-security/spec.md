# Application Security — спецификация

Изменение: add-application-security · Владелец: @platform-frontend.
Предпосылка демо: спека согласована с владельцем до начала работы. Это договорённость, а не автоматически проверенный факт.
Спека говорит, что должно получиться. Как это принято делать в этом репозитории и чем проверять — ищи в самом
репозитории. Ключевые слова OpenSpec (Requirement, Scenario, WHEN/THEN, SHALL) оставлены на английском.

## Публичный контракт
После мёржа не меняется: на это опираются ссылки пользователей и автотесты.

| Контракт | Значение |
|---|---|
| Пункт меню | Application Security |
| Роут (`routePath` = `path` в роуте) | `/application-security` |
| `id` в manifest (`data-testid` пункта меню) | `application-security-microfrontend` |
| Entry (`entryPath` / `outputFileName`) | `/application-security.js` / `application-security.js` |
| Префикс API | `/api/mf/application-security` |
| Проекты и workspaces | `application-security-client`, `application-security-server` |

## Данные (минимум)
- Сервер продукта отдаёт фиксированный демонабор под префиксом API, как `/api/users` у users-and-roles:
  без внешних источников и без записи.
- У записи минимум: идентификатор приложения (длинная строка), название и статус безопасности.
- Записей хватает на несколько страниц. Делить на страницы на клиенте или на сервере — решает реализация.

## ADDED Requirements

### Requirement: Страница инвентаря Application Security
Shell SHALL показывать пункт «Application Security» и открывать таблицу приложений с пагинацией по `/application-security`.

#### Scenario: открыть из меню
- WHEN пользователь нажимает «Application Security»
- THEN открывается таблица приложений; есть состояния loading, empty и error
- AND код страницы скачивается только в этот момент (lazy-чанк)
- AND длинные идентификаторы не ломают вёрстку таблицы

#### Scenario: уйти после пагинации
- WHEN пользователь листает до последней страницы и уходит со страницы
- THEN код приложения не держит detached DOM-узлы

#### Scenario: открыть по ссылке
- WHEN пользователь перезагружает `/application-security` или открывает сохранённую ссылку
- THEN открывается та же страница, а не Not Found

#### Scenario: листать инвентарь
- WHEN пользователь переходит на следующую страницу
- THEN новые записи заменяют текущие, номер страницы виден
- AND на последней странице переход вперёд недоступен

#### Scenario: ошибка API
- WHEN запрос инвентаря падает или возвращает не список
- THEN страница показывает ошибку с кнопкой «Повторить»
- AND «Повторить» запрашивает инвентарь заново и после успешного ответа показывает таблицу
- AND остальной shell и другие продукты в меню продолжают работать

### Requirement: Стандартная архитектура микрофронта
Application Security SHALL быть новым микрофронтом в `src/microfrontends/application-security/`,
устроенным так же, как существующие микрофронты этого репозитория.

#### Scenario: деплоится отдельно
- WHEN продукт собран
- THEN у него свои client, server и manifest, и он зарегистрирован там же, где остальные микрофронты
- AND пункт меню и роут берутся из manifest и модуля роута, а не прописаны в shell

#### Scenario: без второго рантайма
- WHEN diff проходит ревью
- THEN в нём нет Module Federation, script-loader, своего реестра или механизма sharing
- AND React, React DOM, JSX-рантайм и React Router не попадают в бандл продукта
- AND ни один микрофронт не импортирует другой

### Requirement: Lazy-загрузка страницы
Регистрация продукта SHALL NOT добавлять код страницы в стартовый бандл shell.

#### Scenario: отдельный чанк
- WHEN продукт собран в production
- THEN в сборке продукта есть отдельный чанк страницы
- AND стартовый бандл shell и entry продукта не раздуты кодом страницы и библиотеками целиком

#### Scenario: чанк грузится через shell
- WHEN пользователь открывает `/application-security` через shell
- THEN чанк страницы приходит через shell как JavaScript, и страница отрисовывается

### Requirement: Жизненный цикл ресурсов
Ресурсы, которые страница захватила, SHALL освобождаться при размонтировании.

#### Scenario: уход со страницы
- WHEN пользователь уходит со страницы
- THEN таймеры, observer'ы, listener'ы, подписки и незавершённые запросы страницы освобождены

#### Scenario: проверка памяти
- WHEN повторяемый сценарий листает инвентарь до последней страницы и уходит со страницы
- THEN в памяти нет detached DOM-узлов этой страницы
- AND сценарий для этого роута добавлен в репозиторий тем же способом, что и для существующих страниц

### Requirement: Стоимость рендера
Пересчёт строк инвентаря SHALL выполняться только при изменении данных или номера страницы.

#### Scenario: посторонний рендер
- WHEN shell ререндерится по постороннему поводу (например, свернули меню)
- THEN строки инвентаря не пересчитываются, таблица не перемонтируется, текущая страница сохраняется

## Если упёрся
Если lazy-чанк не собирается или не грузится через shell, можно менять конфиг только этого микрофронта
(Babel, webpack, его сервер). Опиши обход в отчёте.

## Вне scope
- редактирование, фильтры, экспорт
- изменения в `src/microfrontends/common/`, shell или других продуктах

Служебная регистрация нового продукта входит в задачу: `package.json` (workspaces и скрипты запуска),
`nx.json`, `tsconfig.json`, `package-lock.json`. Это не разрешение менять поведение shell или `common/`.

## Definition of Done
- Каждый requirement подтверждён проверкой, которую можно повторить: команда и её вывод, а не слова «проверил».
- Зелёная сборка — не доказательство: отдельный чанк, его загрузка через shell, память после пагинации и
  стоимость рендера проверяются каждый своим способом, принятым в этом репозитории.
- Что не удалось проверить в этом окружении, помечай как непроверенное, а не как пройденное.
- В отчёте: что сделал, какие проверки запускал и их результат, ключевые решения, отвергнутые альтернативы и сомнения.
