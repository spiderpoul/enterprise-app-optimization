# Субагенты

Каждый файл здесь описывает субагента, которого основной агент вызывает как функцию: узкий вход,
description, который говорит, когда его звать, разрешённые инструменты и фиксированный формат ответа
с лимитом строк и ссылками file:line. Все субагенты только читают — `explorer` исследует,
`log-analyst` читает длинный вывод, `reviewer` смотрит на готовый diff свежим контекстом. Код меняет
только основной агент.

## Как субагент попадает в работу
1. **Автоматически, по description.** Агент видит description всех субагентов и сам решает позвать
   того, чья задача подходит: «как это сделано сейчас и кто зависит» → `explorer`, длинный лог → `log-analyst`.
   Поэтому description пишем как условие вызова, а не как рекламу.
2. **Из шага скилла или спеки.** Процедура прямо называет субагента: шаг 2 в
   `openspec/changes/add-application-security/tasks.md`, шаг 2 скилла `safe-change`, шаг 2 скилла
   `story-analysis` → `explorer`; шаг 8 в tasks.md → `reviewer`.
3. **Явно, по имени.** Человек пишет в промпте «попроси explorer…» или упоминает его через `@explorer`.

## Синтаксис
Синтаксис frontmatter отличается между агентными CLI: названия полей, способ перечислить инструменты,
каталог, который CLI читает. Адаптируй frontmatter или сделай симлинк на эти файлы там, где твой CLI
ищет агентов, а тело файла оставь как есть.

## Ревьюеры критичных путей
Кроме `reviewer` есть специализированные ревьюеры: `platform-reviewer`, `security-reviewer`, `contract-reviewer`,
`harness-reviewer`. Их не выбирают ни по description, ни руками: `.agents/review/critical-paths.yml`
сопоставляет изменённые пути с ревьюером, `scripts/select-reviewers.cjs` печатает список, а CI
(`.github/workflows/agent-review.yml`) запускает каждого вместе с обычным ревью по скиллу `code-review`.
Они тоже только читают и никогда не одобряют — решает человек из CODEOWNERS.
