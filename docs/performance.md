# Производительность фронтенда
Владелец: @perf-guild · Проверено: 2026-09 · Проверки: npm run check:bundle, npm run check:memory

## Как сейчас правильно
1. Страницу продукта подключай через lazy-роут: React.lazy + Suspense в элементе роута.
2. Клиентский код — только ES-модули: import/export и свой client/babel.config.cjs с modules: false.
3. Кто создал observer, таймер или подписку, тот и снимает их в cleanup эффекта.
4. Компоненты объявляй на уровне модуля, тяжёлые вычисления пересчитывай при смене данных, а не на каждый рендер.
Таблицу с пагинацией проверяй сценарием MemLab на базе tests/memlab/create-route-pagination-scenario.js.

## Не копируй: код работает, но так делать нельзя
| Что                                 | Где встретишь                   | Почему нельзя                       |
|-------------------------------------|---------------------------------|-------------------------------------|
| CommonJS: require(), modules: 'cjs' | корневой babel.config.cjs       | entry больше¹, import() без чанка   |
| статический import страницы         | users-and-roles/client/index    | код страницы в стартовом бандле     |
| тяжёлый расчёт прямо в рендере      | визард React Perf, HeavyBlock   | ~150 мс блокировки на каждый ввод   |
| useAutoTrimCells                    | DeviceSecurityPage, PR #28      | держит DOM-ячейки в Map навсегда    |

¹ Пример прошлого замера: entry users-and-roles 8,4 МБ с корневым Babel и 5,9 МБ с `modules: false`
(production-сборка клиента, размер файла entry). Команда и commit замера не зафиксированы, поэтому это
иллюстрация, а не baseline: с `performance/bundle-baseline.json` напрямую не сравнивай — там байты entry
из текущей сборки `npm run check:bundle`.

## Подводные камни
- CommonJS не видно ни в сборке, ни в тестах: страница работает, а entry растёт (в примере выше —
  8,4 МБ вместо 5,9 МБ) — из `require()` webpack не вырезает неиспользуемый код, и antd с иконками
  едут целиком, а `import()` становится `require()` и не создаёт чанк. Рост entry относительно baseline
  ловит npm run check:bundle — для продуктов, которые есть в baseline.
- Утечку не видно ни в сборке, ни в тестах: страница работает, а после 40 страниц
  пагинации память только растёт. Показывает её MemLab-сценарий этого роута (npm run check:memory).
- Тяжёлый расчёт в рендере не выглядит ошибкой: код короткий и понятный. А в фильтре
  визарда каждое нажатие клавиши блокирует UI на ~150 мс. Видно только в React Profiler.
- `import()` в продукте без своего Babel-конфига не создаёт чанк, а чанк с publicPath «/»
  через shell не загрузится — см. «Lazy-чанки через shell» в docs/architecture/microfrontends.md.

## Старт

Зависимости между шагами инициализации описаны явно. Независимые блокирующие шаги не ждут друг друга без причины, а неблокирующая инициализация не задерживает интерактивный UI. Важен правильный граф зависимостей, а какой Promise-комбинатор для этого взять — дело второе.

Проверка: если меняется поведение старта, разбери граф зависимостей инициализации и замерь, когда UI становится интерактивным. `check:startup` нет специально: пока этот замер не получается сделать стабильным.

## Бандл и загрузка

Каждый роут продукта грузится своим lazy-чанком. Код фичи не попадает в стартовый бандл shell, нужные lazy-чанки собираются, стартовые ассеты укладываются в допуск baseline. Общие runtime-зависимости не дублируются в бандле микрофронта.

Проверка: `npm run check:bundle`. Для расследования — `npm run analyze`. Baseline сейчас покрывает
стартовые ассеты shell-client, operations-reports-client и users-and-roles-client. Entry нового продукта
скрипт не сравнивает, пока его не добавят в baseline: это отдельное решение @perf-guild, временного
бюджета «по умолчанию» нет. Отдельный JS-файл в dist продукта — ещё не доказательство, что страница
грузится лениво: это подтверждает smoke в браузере.

В микрофронте один `import()` чанк не создаёт (корневой Babel-конфиг превращает его в `require()`), а чанк ещё должен быть доступен через shell. Прежде чем чинить «lazy-чанк не собран», прочитай «Подводные камни» и «Lazy-чанки через shell» в `docs/architecture/microfrontends.md`.

## Рендер React

Компонент не перемонтируется, если это не задумано. Тяжёлая синхронная работа не повторяется на посторонних ререндерах. Замеряй конкретное действие и вычисление; мемоизация и debounce — варианты решения, а не обязательные правила.

Проверка: lint и сборка, а для изменений, которые влияют на рендер, — запись React Profiler или performance-трейс в браузере.

## Память и жизненный цикл DOM

После навигации долгоживущие структуры приложения не держат detached DOM-узлы. Ресурсы и observer'ы освобождаются в cleanup, когда компонент размонтируется.

Проверка: подними приложение в режиме, близком к prod, на `MEMLAB_APP_BASE_URL` и явно передай сценарий роута, который менял, например `npm run check:memory -- tests/memlab/device-security.scenario.js`. Сценарий собирается на базе `tests/memlab/create-route-pagination-scenario.js`: выполняет действие, проверяет, что страница пагинации правда сменилась, уходит со страницы и ждёт, пока исходная страница исчезнет, чтобы MemLab сравнил снапшоты. Сценарий другого роута про твой роут ничего не доказывает.

`check:memory` — запуск сценария и анализа MemLab, а не гейт: `memlab run` завершается с кодом 0 и тогда, когда нашёл утечки. Результат читай в выводе: `MemLab found N leak(s)` или `No leaks found`, и приводи эту строку в отчёте.
